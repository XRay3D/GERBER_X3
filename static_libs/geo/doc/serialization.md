# Сериализация (JSON)

Заголовок: [`include/geo/geo_json.h`](../include/geo/geo_json.h).

Geo сам не зависит от движка сериализации проекта (`common/serial.h`) — он
лишь **повторно объявляет** первичный шаблон `Serial::Adapter` (сигнатуры
обязаны совпадать) и специализирует его для своих типов. Тела адаптеров
живут в `polyline.cpp` и `polygon.cpp`, потому что `Polygon::Impl` виден
только там — PIMPL и Qt-базы (`QPointF`) рефлексией движка не взять, отсюда
и явные специализации, а не автоматическая рефлексия, которой сериализуются
обычные структуры проекта.

```cpp
template <> struct Adapter<Geo::Vertex>   { static void write(...); static simdjson::error_code read(...); };
template <> struct Adapter<Geo::Polyline> { /* … */ };
template <> struct Adapter<Geo::Polylines>{ /* … */ };
template <> struct Adapter<Geo::Polygon>  { /* … */ };
template <> struct Adapter<Geo::Polygons> { /* … */ };
```

## Кодировка

Короткие ключи — полилинии доминируют в размере файла; чтение толерантно,
отсутствие ключа означает значение по умолчанию.

| Тип | JSON |
|---|---|
| `Vertex` | `[x, y]` или `[x, y, bulge]` (третий элемент — только если `bulge != 0`) |
| `Polyline` | `{"c": true?, "w": width?, "v": [Vertex...]}` (`"c"`/`"w"` — только если не по умолчанию) |
| `Polygon` | `{"o": Polyline, "h": [Polyline...]?, "i": true?}` (`"h"`/`"i"` — только если непусто/`true`) |
| `Polygons` | `[Polygon...]` |

`Polygon` пишется как граница плюс свои дырки, `Polygons` — **поштучно**, а
не плоским списком контуров: в плоском виде вложенность выражена одной
ориентацией, и остров внутри дырки при чтении вычелся бы вместе с ней (та
же причина, по которой конструктор
[`Polygons(span<Polygon>)`](polygon-and-polygons.md#три-конструктора--три-источника-вложенности)
существует отдельно от плоского списка).

## Что переживает round-trip, а что нет

**Округление до `double`.** Сериализация идёт через **контуры**
(bulge-вид), а не через точное представление CGAL: последнее рационально
(числа неограниченной длины), и укладывать его в поток незачем — при чтении
регион всё равно строится заново тем же свипом, что и при любом другом
входе. Плата — округление координат до `double`, ровно то же, что и при
всякой выдаче геометрии наружу (`toPath()`, `outer()`/`holes()`).

Замерено: дырка диаметром `0.01` мм переживает round-trip, `0.001` мм
пропадает — порог около микрона, на порядки мельче всего, что бывает на
плате (типовой зазор `0.1–0.2` мм, самая мелкая вскрышка — десятки микрон).
См. тест [`smallHolesSurviveSerialization`](../tests/test_polygon.cpp).

**Не пишется, а выводится из вершин.** Ни габарит, ни площадь в JSON не
хранятся — они целиком выводятся из вершин при чтении.

**Переживает без потерь:**

* вложенность региона (`Polygons` пишется поштучно, тесты
  [`regionWithIslandInHoleSurvivesSerialization`](../tests/test_polygon.cpp),
  [`denseRegionWithArcIslandsSurvivesSerialization`](../tests/test_polygon.cpp)),
* флаг [`Polygon::isInverted()`](polygon-and-polygons.md#invert--ленивая-пометка-это-пустота)
  (`"i": true`),
* ориентация внешней границы после чтения не разворачивается вторично —
  контуры пишутся уже каноническими.
